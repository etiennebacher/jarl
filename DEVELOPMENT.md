# Development notes

## Make a new pre-release

1. Bump the version number in all `Cargo.toml` files and in `Cargo.lock` (automatically changed). Use for instance `x.y.z-alpha.1`.
1. Manually trigger the "Release" workflow (**not the "Release workflow to run" workflow** because it triggers some docs changes and triggers a new PyPI release that we don't want here) and give it the same version number. `cargo-dist` will automatically create a pre-release instead of a release.

## Make a new release

1. Bump the version number in all `Cargo.toml` files and in `Cargo.lock` (automatically changed).
1. Update the version number in changelog.
1. Manually trigger the "Release workflow to run" workflow (**not the "Release" workflow**, that is automatically generated by `cargo-dist`) and give it the same version number. If the version number contains "alpha", `cargo-dist` will automatically create a pre-release instead of a release.

NOTE: a successful Github (stable) release triggers:

- a documentation re-build for the "stable" version of the website, picking the latest tag as the "stable" version to display.
- a new release on PyPI
- a new release of the extension on OpenVSX and VS Code Marketplace

To make a new release for the extension (for instance for a fix specific to the extension and not related to Jarl itself), bump the version in `/editors/code/package.json`, add a changelog item in the README, and manually trigger the "Release extension" workflow.
